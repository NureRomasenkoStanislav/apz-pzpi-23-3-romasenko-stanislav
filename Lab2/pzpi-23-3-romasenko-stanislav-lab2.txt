2 ЗАВДАННЯ
Спроектувати та реалізувати клієнтську частину програмного комплексу RoomBook у форматі кросбраузерного веб-застосунку (Single Page Application). Продукт має забезпечувати віддалений доступ користувачів до сервісів бронювання, а також надавати інструменти оперативного адміністрування інфраструктури об'єкта.
Веб-інтерфейс повинен підтримувати два незалежних сценарії використання:
    1. Режим відвідувача (User Mode): візуальний моніторинг доступного фонду аудиторій, перегляд лімітів місткості, формування запитів на резервування обраних часових інтервалів.
    2. Режим керування (Admin Mode): повний CRUD-цикл адміністрування кімнат (внесення нових об'єктів, коригування текстових описів, зміна параметрів місткості, блокування та архівування).
Додатково веб-застосунок має містити засоби мовної локалізації, динамічної адаптації інтерфейсу під поточну роль авторизованої сесії та стійку систему клієнтської валідації типів даних.

3 ТЕХНІЧНИЙ ОПИС ТА ПРИЙНЯТІ ІНЖЕНЕРНІ РІШЕННЯ
Веб-орієнтована консоль управління RoomBook Operations Console реалізована як сучасний SPA-застосунок на базі бібліотеки React 18 та швидкісного збирача Vite. Уся логіка управління станом зосереджена безпосередньо в середовищі виконання браузера за допомогою декларативного підходу та вбудованих інструментів реактивності (React Hooks).
3.1 Опис прийнятих інженерних рішень
Архітектурне розділення UI та сервісного шару (Service Layer Separation): Для забезпечення чистоти коду вся мережева логіка повністю інкапсульована всередині окремого драйвера — src/apiService.js. Екранні компоненти не містять сирих викликів асинхронних запитів чи явних URL-адрес. Взаємодія з інтерфейсами системи реалізована через високорівневі методи (getRooms, createBooking, createRoom), що повертають уніфіковані проміси (Promises).
Ізоляція та безпека сесії на стороні клієнта: Після успішної автентифікації клієнтська частина фіксує криптографічний JWT-токен доступу. Будь-який запит на зміну стану даних автоматично забезпечується заголовком Authorization: Bearer {token} безпосередньо у сервісному шарі, що виключає необхідність дублювання авторизаційного коду в різних частинах інтерфейсу.
Рольовий умовний рендеринг (Role-Based UI Filtering): На відміну від мобільної платформи, де перемикання екранів вимагало глибокої перебудови стеку фрагментів, у веб-застосунку застосовано гнучку фільтрацію DOM-дерева на основі стану (isAdmin). Елементи керування інфраструктурою кімнат рендеряться в браузері виключно за умови наявності прав рівня Administrator.
Автоматична підготовка даних до специфікацій зовнішніх моделей: Веб-клієнт самостійно координує типи даних перед відправкою форм. Зокрема, реалізовано автоматичне приведення числових значень (parseInt(capacity)) та впровадження обов’язкових часових констант роботи (WorkingHoursStart / WorkingHoursEnd у стандартному рядковому форматі hh:mm:ss), що нівелює ризики отримання помилок валідації моделей на етапі обробки запитів.
3.2 Взаємодія компонентів веб-застосунку
Вся комунікація клієнтських модулів орієнтована на єдину точку входу BASE_URL = "https://localhost:7242".
    • Головний компонент (App.jsx): Виступає базовим оркестратором системи (Shell Layer). Він зберігає у стані токен авторизації, ініціює зміну мовних пакетів та вирішує, який саме інтерфейс відобразити користувачу після проходження авторизаційного екрана.
    • Сервісний шлюз (apiService.js): Виконує роль транслятора даних. Він приймає параметри від UI-компонентів, збирає фінальні JSON-об'єкти, налаштовує HTTP-заголовки, відправляє запити та здійснює первинний парсинг статусів відповідей (включаючи коректну обробку порожнього контенту зі статусом 204 NoContent).
    • Панель адміністратора (AdminPanel.jsx): Інтерактивна консоль, що взаємодіє із сервісним шаром для виконання CRUD-операцій. Вона обладнана універсальним механізмом маппінгу властивостей (Property Mapping), що дозволяє безпомилково зчитувати параметри об'єктів кімнат із масиву незалежно від регістру літер, у якому їх надіслав сервер.
    • Кабінет користувача (UserPanel.jsx): Спрощений клієнтський модуль, призначений для швидкого моніторингу списку кімнат у режимі реального часу та генерації запитів на резервування (createBooking).

В.1 Хронологія та сутність інженерних запитів
В.1.1 Запит 1: Реалізація багатомовності (i18n) у межах SPA-архітектури
    • Назва інструменту та версія: Google Gemini 1.5 Pro
    • Мета використання: Пошук оптимального підходу для інтеграції інтернаціоналізації (UA/EN) в односторінковий веб-застосунок без перезавантаження сторінок.
    • Внесок автора: Студент самостійно налаштував JSON-файли локалізації, інтегрував перемикач мов у головну панель App.jsx та пов'язав текстові константи з реактивним хуком перекладу.
    • Початковий запит: «Як найкраще реалізувати підтримку двох мов (української та англійської) у React-додатку на Vite, щоб тексти змінювалися миттєво при кліку на кнопку, а обрана мова зберігалася після оновлення сторінки?»
    • Відповідь: Для цього доцільно використати бібліотеку i18next разом із react-i18next. Тексти виносяться в окремі локальні JSON-словники. Хук useTranslation забезпечує динамічну підміну рядків за ключами у JSX-розмітці, а плагін LanguageDetector автоматично зберігає вибір користувача у cookies або localStorage, що запобігає скиданню налаштувань.
В.1.2 Запит 2: Клієнтська обробка статусів HTTP-відповідей
    • Назва інструменту та версія: Google Gemini 1.5 Pro
    • Мета використання: Проектування уніфікованого перехоплювача помилок для асинхронних запитів клієнта до серверних ендпоінтів.
    • Внесок автора: Автор адаптував логіку обробки HTTP-статусів у apiService.js, додавши специфічні розгалуження для пустих відповідей (код 204) та помилок доступу (коди 401/403).
    • Початковий запит: «Як у JavaScript-модулі асинхронних запитів (Fetch API) правильно обробляти різні відповіді сервера, якщо при видаленні кімнати він повертає статус 204 No Content, а при закінченні дії токена — 401 Unauthorized?»
    • Відповідь: При використанні Fetch API слід перевіряти властивість response.ok. Якщо сервер повертає статус 204, метод json() викликати не можна, оскільки тіло відповіді порожнє — у цьому випадку проміс має просто повертати успішний статус. Для статусів 401 або 403 необхідно згенерувати виняток throw new Error, який буде перехоплений екранним компонентом для автоматичного перенаправлення користувача на форму входу.
В.1.3 Запит 3: Оптимізація рендерингу великих масивів даних
    • Назва інструменту та версія: Google Gemini 1.5 Pro
    • Мета використання: Забезпечення стабільної продуктивності клієнтського інтерфейсу під час відображення великої кількості об'єктів у таблицях.
    • Внесок автора: Студент впровадив унікальні ключі (key={room.RoomId}) для циклів рендерингу в AdminPanel.jsx та реалізував клієнтську фільтрацію масиву кімнат для швидкого пошуку.
    • Початковий запит: «Чому React вимагає обов'язкове поле key при маппінгу масиву кімнат через .map() для виведення списку в UI, і як це впливає на швидкість роботи веб-застосунку?»
    • Відповідь: Поле key необхідне для алгоритму порівняння Віртуального DOM (Reconciliation). Воно допомагає React чітко ідентифікувати, які саме елементи масиву змінилися, були додані або видалені. Без унікального ключа (наприклад, RoomId) при будь-якій модифікації однієї кімнати браузер буде примусово перемальовувати весь список, що суттєво знижує швидкість відгуку інтерфейсу.
