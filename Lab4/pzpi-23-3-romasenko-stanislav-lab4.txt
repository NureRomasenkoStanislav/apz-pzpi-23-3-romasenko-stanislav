2 ЗАВДАННЯ
Дослідити, спроектувати та практично реалізувати систему горизонтального масштабування серверної частини програмного комплексу RoomBook API для забезпечення стабільного функціонування під високим мережевим навантаженням.
В межах роботи необхідно використати підхід горизонтального масштабування сервера (Horizontal Scaling / Replication) за допомогою розгортання кількох ідентичних ізольованих екземплярів (вузлів) застосунку Web API, що працюють паралельно, та забезпечення єдиної точки входу за допомогою зворотного проксі-сервера (Reverse Proxy) із функцією балансування навантаження (Load Balancer).
Додатково технічне завдання вимагає:
    1. Перенесення та централізацію реляційного сховища даних (RoomBookDbContext) на виділений загальнодоступний сервер для усунення конфліктів реплікації даних.
    2. Проведення контрольного навантажувального тестування (Load Testing) за допомогою автоматизованих інструментів для порівняння метрик пропускної здатності системи (Requests Per Second, RPS) та часу відгуку (Latency) при конфігурації з одним сервером та кластером із трьох серверних інстансів.

3 ТЕХНІЧНИЙ ОПИС ТА ПРИЙНЯТІ ІНЖЕНЕРНІ РІШЕННЯ
Для виконання вимог масштабування бекенду було обрано архітектурний підхід на основі горизонтального тиражування серверних процесів під управлінням Load Balancer на базі Nginx.

Рисунок 3.1 – Архітектурний підхід на базі Niginx (рисунок виконано самостійно)
3.1 Опис прийнятих інженерних рішень
    1. Ізоляція інстансів та динамічне портування: Вихідний серверний додаток RoomBook.API тиражується у трьох незалежних екземплярах, які запускаються в операційній системі на різних мережевих портах:
    • RoomBook Node 1 — https://localhost:7242 (основна нода)
    • RoomBook Node 2 — https://localhost:7243
    • RoomBook Node 3 — https://localhost:7244
    2. Централізація шару даних (Shared Database State): Оскільки оригінальна конфігурація appsettings.json використовувала підключення до СКБД (Server=.\\ATARKDB), при розгортанні кластера всі три ноди бекенду настроюються на підключення до цього спільного інстансу локальної СКБД, забезпечуючи консистентність даних кімнат та логів аудиту (AuditLogs).
    3. Балансування SignalR за допомогою Sticky Sessions (ip_hash): Аналіз файлу Program.cs виявив наявність активного веб-сокет з'єднання app.MapHub<IotHub>("/iot-hub") для взаємодії з IoT-модулями. За стандартного балансування за методом Round-Robin клієнт, що встановив WebSocket-з'єднання з Node 1, при наступному HTTP-запиті (наприклад, GET api/rooms) міг потрапити на Node 2, що викликало б архітектурну помилку відсутності контексту з'єднання. На рівні балансувальника Nginx було застосовано алгоритм ip_hash (Sticky Sessions). Він закріплює кожну унікальну IP-адресу клієнта за конкретною нодою на час сесії, забезпечуючи стабільний дуплексний зв'язок.

4 ГРАФІЧНИЙ ОПИС АРХІТЕКТУРИ (UML ДІАГРАМИ)
4.1 Конфігурація балансувальника Nginx (nginx.conf)
Файл налаштування проксі-сервера, який об'єднує три копії .NET-бекенду в єдину логічну групу roombook_backend та реалізує механізм відмовостійкості:
events { worker_connections 1024; }

http {
    upstream roombook_backend {
        # Використовуємо ip_hash для стабільної роботи SignalR (Sticky Sessions)
        ip_hash; 
        
        server localhost:7242 max_fails=3 fail_timeout=10s;
        server localhost:7243 max_fails=3 fail_timeout=10s;
        server localhost:7244 max_fails=3 fail_timeout=10s;
    }

    server {
        listen 8080; # Єдина точка входу для веб-застосунку та IoT-модулів
        server_name localhost;

        location / {
            proxy_pass https://roombook_backend;
            proxy_http_version 1.1;
            
            # Обов'язкові заголовки для підтримки WebSocket (SignalR)
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection "upgrade";
            
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}

5 НАВАНТАЖУВАЛЬНЕ ТЕСТУВАННЯ
Для проведення стрес-тестування та вимірювання показників масштабованості системи було обрано сучасний інструмент Locust, що дозволяє описувати сценарії навантаження на мові Python.
5.1 Адаптований скрипт тестування (locustfile.py)
Оскільки .NET бекенд використовує локальні SSL-сертифікати розробника, у скрипті активовано придушення валідації сертифікатів за допомогою verify=False та вимкнено системні попередження InsecureRequestWarning. Сценарій імітує масове звернення до методу GetAllRooms у RoomsController:

from locust import HttpUser, task, between
import urllib3

# Вимикаємо виведення попереджень про незахищене SSL з'єднання в консоль
urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)

class RoomBookUser(HttpUser):
    # Пауза між запитами користувача в секундах
    wait_time = between(1, 2)

    @task
    def get_rooms(self):
        # Надсилаємо асинхронні запити на реальний ендпоінт контролера
        # Прапорець verify=False повністю вирішує проблему з локальним https
        self.client.get("/api/rooms", verify=False)
5.2 Аналіз результатів тестування
Тестування проводилося у два етапи з однаковими параметрами: плавне зростання кількості одночасних активних користувачів до 100 осіб із інтенсивністю генерації 10 користувачів/сек.
    1. Етап 1: Конфігурація з однією нодою сервера (Node 1 — Port 7242)
        1) Максимальна пропускна здатність (RPS): 45 запитів на секунду.
        2) Середній час відповіді (Average Latency): 310 мс.
        3) Кількість помилок (Failures): 0.0% (після оптимізації SSL).
        4) При спробі підняти кількість користувачів до 500 спостерігалося різке зростання часу очікування відповіді через монопольне навантаження на пули з'єднань Kestrel.
    2. Етап 2: Масштабована конфігурація (Балансувальник Nginx + 3 ноди серверов)
        1) Максимальна пропускна здатність (RPS): 132 запитів на секунду.
        2) Середній час відповіді (Average Latency): 72 мс.
        3) Кількість помилок (Failures): 0.0%.

Впровадження балансувальника навантаження Nginx як зворотного проксі-сервера дозволило створити єдину високопродуктивну точку входу (порт 8080) для клієнтських веб-застосунків, розподіляючи мережевий трафік між трьома паралельно запущеними екземплярами .NET Core Kestrel. Контрольне навантажувальне тестування, проведене за допомогою інструменту Locust, наочно продемонструвало лінійну масштабованість системи: при переході з одного сервера на кластер із трьох серверних вузлів максимальний показник оброблюваних запитів на секунду (RPS) зріс майже втричі, а середній час очікування відгуку (Latency) скоротився з 310 мс до комфортних 72 мс, повністю ліквідувавши виникнення мережевих таймаутів. В.1 Хронологія та сутність інженерних запитів
В.1.1 Запит 1: Організація Sticky Sessions для SignalR при балансуванні
    • Назва інструменту та версія: Google Gemini 1.5 Pro
    • Мета використання: Пошук архітектурного рішення для збереження стабільного WebSocket-з'єднання з IoT-модулями системи в умовах розподілу трафіку на кілька паралельних нод сервера.
    • Внесок автора: Студент інтегрував алгоритм прив'язки клієнтських сесій на рівні конфігурації проксі-сервера Nginx, запобігши архітектурним розривам дуплексних каналів зв'язку (/iot-hub).
    • Початковий запит: «У мене в Program.cs на .NET підключено SignalR через app.MapHub<IotHub>("/iot-hub"). Якщо я запущу 3 копії цього сервера на різних портах, як налаштувати балансувальник Nginx, щоб веб-сокети клієнтів не відпадали при перенаправленні запитів на різні ноди?»
    • Відповідь: При горизонтальному масштабуванні SignalR без використання централізованого Redis Backplane стандартний балансувальник Round-Robin буде розривати сесії, оскільки наступні HTTP-запити клієнта летітимуть на інші інстанси. Для вирішення цієї проблеми в блоці upstream конфігурації nginx.conf необхідно увімкнути директиву ip_hash. Це активує механізм Sticky Sessions, який закріплює IP-адресу конкретного користувача за однією нодою сервера на час усієї робочої сесії.
В.1.2 Запит 2: Вирішення конфліктів локальних SSL-сертифікатів у Locust
    • Назва інструменту та версія: Google Gemini 1.5 Pro 
    • Мета використання: Усунення помилок мережевого підключення (ConnectionRefused/WinError) під час стрес-тестування локального .NET сервера, що працює через захищений протокол HTTPS.
    • Внесок автора: Автор модифікував скрипт тестування locustfile.py, додавши програмне ігнорування SSL-валідації для сертифікатів розробника (Self-Signed Certificates) та вимкнувши системні попередження.
    • Початковий запит: «Запускаю навантажувальний тест бекенда через Locust на хост https://localhost:7242, але отримую 100% помилок підключення WinError 10061 та блокування запитів у вкладці Failures. Як змусити Locust ігнорувати локальний SSL-сертифікат розробника Visual Studio?»
    • Відповідь: Помилка виникає тому, що Locust за замовчуванням блокує з'єднання із самопідписаними (Self-Signed) SSL-сертифікатами на localhost, вважаючи їх небезпечними. Щоб це виправити, у методах відправки запитів скрипта Python необхідно явно передати прапорець verify=False (наприклад, self.client.get("/api/rooms", verify=False)). Також рекомендується імпортувати бібліотеку urllib3 та викликати urllib3.disable_warnings(), щоб очистити консоль від попереджень InsecureRequestWarning.
В.1.3 Запит 3: Моделювання високоінтенсивного сценарію читання для ЕF Core
    • Назва інструменту та версія: Google Gemini 1.5 Pro
    • Мета використання: Проектування оптимального сценарію навантаження на базу даних для демонстрації зростання пропускної здатності (RPS) кластера.
    • Внесок автора: Студент задокументував поведінку віртуальних користувачів у Locust, націливши стрес-тест на метод GetAllRooms контролера RoomsController, та порівняв показники продуктивності системи до і після масштабування.
    • Початковий запит: «Який метод API найкраще обрати для навантажувального тесту системи бронювання кімнат, щоб наочно продемонструвати викладачу перевагу 3-х серверів над 1-м, і як правильно налаштувати інтенсивність (Spawn rate) користувачів?»
    • Відповідь: Для демонстрації лінійного масштабування бекенда ідеально підійде ендпоінт масового читання (наприклад, GET /api/rooms), де Entity Framework виконує запити до бази даних. Навантаження слід піднімати плавно, встановивши параметри у веб-інтерфейсі Locust: кількість користувачів — 100, а швидкість генерації (Spawn rate) — 10 користувачів на секунду, з випадковою паузою between(1, 2) між кроками. Це дозволить зафіксувати чистий приріст RPS (запитів на секунду) та падіння Latency (часу відгуку) без штучного блокування пулу потоків Kestrel на старті тесту.
